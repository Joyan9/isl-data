# fotmob-isl

Indian Super League match data from FotMob -> four CSV tables, generated by a scheduled GitHub Actions pipeline and stored in this repo.

## Current repository state

This checkout is the pipeline codebase, not a populated dataset. The ingestion logic is implemented and tested, but the generated CSVs and raw match archives are not yet present under `data/` in this snapshot. The repository is ready to run the pipeline, but actual match data must be fetched and committed by the workflow before the tables are usable.

## Tables (`data/`)

| file | grain | primary key |
|---|---|---|
| `matches.csv` | one row per match: venue, referee (+ FotMob's referee stats), weather, insights, fan vote | `match_id` |
| `team_match_stats.csv` | match x period (`All`/`FirstHalf`/`SecondHalf`) x side x stat | `match_id, period, side, group_key, stat_key` |
| `shots.csv` | one row per shot (shot map: xG, xGOT, coordinates, situation, body part) | `match_id, shot_id` |
| `player_match_stats.csv` | match x player x stat (long format) | `match_id, player_id, group_key, stat_key` |

`data/raw/<match_id>.json.gz` keeps the untouched API response plus a small `_pipeline` block (fetch time, source,
fan vote), ~30 KB each, so parsing can be re-run without re-scraping. Join on `match_id`, `team_id`, `player_id`.

## Notes on the data

- **Referee columns are a snapshot.** `referee_*_per_match` / `_total` / `_league_avg` are FotMob's running figures
  *at the time of the fetch* (`fetched_at_utc`), not as of kick-off, and it's unclear whether they already include
  the match itself. For a defensible "was this referee lenient?" comparison, build baselines from this repo's own
  data: group matches by `referee_id`, take fouls / yellow / red per match from `team_match_stats.csv`
  (`group_key = discipline`, `period = All`), and compare cards *per foul* as well as raw counts.
- `fan_vote_*` are raw vote counts (1x2 poll); `NULL` if the vote endpoint failed. `attendance` is often empty.
- **Own goals** are a row in `shots.csv` with `is_own_goal = True`, empty `xg`/`xgot`, and `team_id` = the team of
  the player who put it in. Use `credited_team_id` for the team the goal counted for.
- **Player stat groups.** The API only has `top_stats`, `attack`, `defense`, `duels`. The site's *Passes* and
  *Goalkeeping* tabs are regroupings (goalkeeper stats such as `saves`, `goals_prevented` sit in `top_stats`).
  Filter by `stat_key`, not by tab.
- `value_num` is numeric; for "512 (88%)"-style stats `value_num` = 512, `value_pct` = 88 (players use `value_total`).
- Team xG vs the sum of shot-level xG can differ slightly (0.012 on the sample match); `validate.py` warns above 0.03.

## Usage

```bash
pip install -r requirements-dev.txt
python -m pytest -q                                   # offline, uses tests/fixtures
python -m fotmob_isl smoke 6361990                    # fetch + parse one match, writes nothing
python -m fotmob_isl discover                         # finished match IDs from the fixtures page
python -m fotmob_isl ingest --match-ids 6361990 --data-dir scratch
python -m fotmob_isl ingest --discover --data-dir scratch      # everything finished and not yet ingested
python -m fotmob_isl ingest --discover --season 2025/2026      # past season (season param unverified)
```

`ingest` skips unfinished matches and anything outside league 9478. Re-ingesting a match replaces its rows, and CSV
output is sorted and deterministic, so git diffs only show real changes. `--discover` implies `--skip-existing`.

The workflow is designed to populate the repo with real data over time, but a fresh checkout may start empty until the scheduled run or a manual run has completed. The `.github/workflows/ingest.yml` job is the live data-producing path.

On GitHub the *ingest* workflow runs daily at 06:00 UTC (`--discover`), or manually via Actions -> *ingest* -> Run
workflow (optionally with match IDs). Public repos: GitHub pauses scheduled workflows after 60 days without repo
activity, which can happen over the off-season.

## Unverified

1. **Runner access.** Works from a Codespace; a GitHub runner uses different IPs. The workflow's smoke step is the
   test. On 401/403 the client falls back to `__NEXT_DATA__` of `https://www.fotmob.com/match/<id>` (URL pattern
   unverified). Fixtures discovery needs the league *HTML* page, so it has no API fallback.
2. `--season` for past seasons relies on the `season` query parameter of the fixtures page.
3. FotMob's terms prohibit automated/systematic access. Keep it low-volume and personal/research, and don't
   republish the raw data.
